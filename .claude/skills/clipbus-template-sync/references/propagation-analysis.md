# 升级影响分析

逐项阅读当前目标、官方模板和相关 SDK 文档，再决定哪些变化适用。本文件提供判断方向，不规定路径清单、版本号或统一文件内容。

## 参考资料各自回答什么

- 目标插件：实际提供什么功能，身份、业务依赖、用户状态、构建与测试如何组织，哪些差异是有意保留。
- 官方模板：当前工程组织与开发方式如何演示，相关构建或工具链变化解决了什么问题。
- 当前与目标 SDK 文档：哪些契约、语义、权限和限制发生变化，哪些迁移是必要的，哪些能力只是可选新增。

没有旧模板副本时，以插件现状和对应 SDK 文档分析兼容性，不把当前模板与插件的每一处差异都视为缺陷。

## 判断是否需要迁移

| 变化 | 需要回答的问题 |
|---|---|
| 删除、改名或改签名 | 插件是否使用，当前文档推荐什么迁移路径，受影响的声明、实现、调用和测试有哪些？ |
| 生命周期、提交或交互语义 | 即使代码能编译，重复处理、失败、状态清理或当前处理值的含义是否改变？ |
| 新增可选能力 | 是否与该插件需求有关，采用它有什么收益与代价，是否属于本次授权范围？ |
| manifest、权限与运行限制 | 是否改变宿主加载、文件访问、安装或现有依赖运行所需条件，真实宿主兼容情况是否已确认？ |
| 构建、安装与开发配置 | 上游变化解决什么实际问题，目标工程是否也存在，如何保留现有布局和业务依赖完成适配？ |
| 示例、样式、预览与测试 | 是工程方法变化还是模板演示业务，目标插件应保留哪些自己的组件、样例和业务向量？ |

还应阅读新增、修改与删除内容，不只看已跟踪文件的 diff。SDK 影响可能写在根文档、迁移指南或教程正文中，不能仅比较导出名称与方法数量。

## 常见误判

- 依赖只改了版本号，不代表行为未变；验证全绿也不能代替阅读迁移语义与相关可选能力。
- 文件位于共享目录，不代表所有插件都需要；模板演示可能使用专用 helper 或构建映射。
- 同一用途的构建脚本可以有不同实现，不要求整个文件或 scripts 段一致。
- 锁文件反映各插件自己的依赖树，保留无关依赖及平台元数据，检查升级是否引入无关重写。
- 试点通过只证明该插件的结果，其余目标仍需按自己的代码与命令验证。
- 已有源码不等于宿主正在加载新的产物；检查实际加载目录，不能沿用旧的验证豁免。
